# Design Principles

ปรัชญาการออกแบบและ debug สำหรับโปรเจกต์นี้ ใช้ร่วมกับ `DESIGN_REVIEW_TEMPLATE.md`
ไฟล์นี้แทบไม่ควรเปลี่ยน — ถ้าจะแก้ ต้องมีเหตุผลระดับโปรเจกต์ ไม่ใช่ระดับ task เดียว

1. **Fact before assumption.**
   แยกสิ่งที่พิสูจน์ได้จาก source code ออกจากสิ่งที่เราคาดเดา เสมอ

2. **Never infer intent without evidence.**
   ถ้าไม่มีหลักฐานว่าโค้ดเดิม "ตั้งใจ" ทำงานแบบไหน ให้บอกว่าสรุปไม่ได้
   อย่าเดาเจตนาแล้วเขียนราวกับเป็นข้อเท็จจริง

3. **Behavior change requires stronger justification than bug fix.**
   ถ้าสิ่งที่จะแก้คือการเปลี่ยนพฤติกรรมที่ตั้งใจไว้แต่แรก (ไม่ใช่แก้ข้อผิดพลาด)
   ต้องอธิบายเหตุผลและผลกระทบละเอียดกว่าการแก้บั๊กทั่วไป

4. **Every design trade-off must identify both false positive and false negative risk.**
   การแก้ปัญหาหนึ่งด้าน (เช่น false alarm) มักแลกกับความเสี่ยงอีกด้าน
   (เช่น ข้อมูลจริงถูกกรองทิ้ง) ต้องระบุทั้งสองด้านเสมอ ไม่ใช่แค่ด้านที่กำลังแก้

5. **Every proposal must identify system invariants.**
   ก่อนเสนอทางแก้ ต้องระบุก่อนว่าอะไรคือสิ่งที่ระบบต้องรักษาไว้ (ห้ามเสีย)
   แล้วพิสูจน์ว่าทางแก้ที่เสนอยังรักษาสิ่งนั้นไว้ครบ หรือระบุชัดว่าแลกอะไรไปเพื่ออะไร

6. **Unknown is preferable to guessed.**
   คำตอบ "ยังไม่ทราบ ต้องตรวจเพิ่ม" มีค่ามากกว่าคำตอบที่เดาแล้วฟังดูมั่นใจ
   โดยเฉพาะกับระบบที่ผลกระทบไปถึง alarm/telemetry ภายนอก

7. **Smallest change first.**
   เลือกการแก้ที่เล็กที่สุดที่แก้ปัญหาปัจจุบันได้ ห้าม large-scale refactoring
   เว้นแต่ถูกร้องขอชัดเจน

---

**North Star**

เป้าหมายไม่ใช่การพิสูจน์ว่าสมมติฐานของเราถูก แต่คือการค้นหาคำอธิบายที่ถูกต้องที่สุด
จากหลักฐาน — ถ้าหลักฐานชี้ไปคนละทางกับที่คาดไว้ ให้เชื่อหลักฐาน ไม่ใช่ปรับหลักฐาน
ให้เข้ากับที่คาดไว้

---

หลักการเหล่านี้ใช้ได้กับทุก subsystem ในโปรเจกต์ (state machine, analytics,
de-glitch, RS485/Modbus, network/MQTT) ไม่ผูกกับปัญหาใดปัญหาหนึ่งโดยเฉพาะ
